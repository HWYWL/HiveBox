## 一、 背景与现状分析

### 1.1 现状与优势
`pomelo-gfx` 是一款直接面向 16 位面板原生像素格式（RGB565）的轻量级 2D 光栅化引擎。
* **原生直绘优势**：通过绕开通用 2D 图形库（如 Skia / tiny-skia）所必须的 4 字节 RGBA8888 画布和二次全屏格式转换开销，纯色矩形填充已实现 ~0.12 µs/像素的高吞吐；
* **硬件浮点利用**：在坐标变换、贝塞尔曲线扁平化（`src/geometry.rs`, `src/path.rs`）中大量使用的 `f32` 运算，已被当前编译工具链（`xtensa-esp32s3-espidf`）自动映射为 Xtensa LX7 的硬件单周期单精度浮点指令（FPU）。

### 1.2 性能瓶颈：纯标量颜色混合（Scalar Blending）
尽管浮点已被硬件化，**像素级的光栅化与颜色混合仍然全部为标量循环**：
1. **逐像素拆解与拼装**：
   在 [src/color.rs](file:///home/edward/Projects/pomelo-project/pomelo-gfx/src/color.rs) 的 `blend_rgb565` 中，每一个像素的 Alpha 混合都必须经历多次移位（`>> 11`, `>> 5`）、整型乘加和除以 255 的运算：
   ```rust
   let r = ((r_s * a + r_d * inv_a + 127) / 255) as u16;
   let g = ((g_s * a + g_d * inv_a + 127) / 255) as u16;
   let b = ((b_s * a + b_d * inv_a + 127) / 255) as u16;
   (r << 11) | (g << 5) | b
   ```
2. **字符与图标蒙版混合（Text / Icon Blit）**：
   在 [src/raster.rs](file:///home/edward/Projects/pomelo-project/pomelo-gfx/src/raster.rs) 的 `blit_mask` 中，文字渲染遍历 8-bit Alpha 蒙版，逐个像素调用标量 `blend_rgb565`，未发生批量并行处理。
3. **编译器自动矢量化的局限**：
   当前 Rust Xtensa 编译器分支（`esp198` / rustc 1.98）的 LLVM 自动矢量化器（Auto-vectorizer）无法自动生成 ESP32-S3 专有的 PIE（Processor Interface Extension）128 位矢量指令。128 位的向量寄存器（`q0`~`q7`）在光栅化阶段处于**闲置状态**。

## 二、 Xtensa PIE 矢量加速技术方案

ESP32-S3 的 Xtensa LX7 核心具备 8 个 128 位矢量寄存器（`q0` 至 `q7`）。一个 128 位寄存器恰好可以同时容纳 **8 个 16 位 RGB565 像素**（$8 \times 2\text{ bytes} = 16\text{ bytes} = 128\text{ bits}$）。

### 2.1 加速切入点与核心函数

| 热点场景 | 目标函数 | 当前实现 | 矢量化改造方案 |
| :--- | :--- | :--- | :--- |
| **文字 / 图标抗锯齿蒙版** | `raster::blit_mask` | 逐像素读取 mask 并调用 `blend_rgb565` | 一次载入 8 字节 mask 与 8 个 dst 像素，单周期完成 8 像素的 Alpha 并行混合 |
| **半透明矩形 / 图层填充** | `raster::fill_rect` (alpha < 255) | 单像素循环 `blend_rgb565` | 批处理 8 像素的恒定颜色 Alpha 混合（定点乘加） |
| **不透明纯色横条填充** | `raster::fill_u16_slice` | 32 位整型写（每次 2 像素） | 升级为 128 位矢量写入（每次 8 像素写，吞吐提升 4 倍） |
| **渐变着色器** | `paint::LinearGradientShader` | 逐像素浮点/整型插值 | 4 像素或 8 像素批处理颜色步进插值 |

### 2.2 算法优化：快速定点数除法（Fast Integer Division）
目前标量实现使用了 `(x + 127) / 255`。在矢量指令中除法极其昂贵，应转换为**定点乘法与移位近似**：
$$\frac{x}{255} \approx \frac{x \times 257 + 257}{65536} = ((x + 1) + (x + 1) \times 256) \gg 16$$
或者最常用的嵌入式经验公式：
$$((x + 1) \times \text{alpha}) \gg 8$$
这使得 8 个像素的颜色混合可以纯粹由 PIE 矢量的 `vadd`、`vmul` 与 `vsrli` 指令在极低周期内完成。

### 2.3 架构设计：条件编译与平台隔离

为了保持 `pomelo-gfx` 在宿主机桌面端（`cargo test`、模拟器）的编译兼容性，矢量实现必须通过条件编译严格隔离：

```text
src/
├── arch/
│   ├── mod.rs               # 导出平台无关的 span 混合 trait
│   ├── fallback.rs          # 纯 Safe Rust 标量实现（用于 x86_64, aarch64 等）
│   └── xtensa_pie.rs        # #[cfg(target_arch = "xtensa")] 下的内联汇编核心
```

提供统一内部 API：
```rust
// 批量处理连续行上的像素混合
pub(crate) fn blend_span_rgb565(dst: &mut [u16], src: u16, alpha: u8);

// 批量处理 8-bit Alpha 蒙版混合
pub(crate) fn blit_mask_span(dst: &mut [u16], mask: &[u8], src: u16, alpha: u8);
```

## 三、 预期性能收益

1. **文字与图标排版渲染性能提升 2x ~ 3x**：
   UI 中大部分脏区为状态栏时间、文字标签或图标刷新。8 像素并行批处理可大幅消除循环开销与分量解包开销。
2. **半透明遮罩与动画帧率翻倍**：
   半透明弹窗、遮罩背景或渐变进度条从当前 ~1.5 µs/像素压缩至 ~0.4 µs/像素以内。
3. **释放 Core 0 算力**：
   降低 GUI 线程绘制一帧的耗时（`paint time`），为 Rune 脚本虚拟机或复杂的组件布局计算留出更多裕量。

## 四、 实施路线规划 (Phases)

- [x] **Phase 1: 算法预演（纯 Rust 定点数优化）**
  - 落地方式与原计划不同：没有新增 `blend_rgb565_fast` 孪生函数，而是把 `blend_rgb565`
    与 `blend_rgb888_onto_rgb565` **自身**的 `/255` 换成 `color::div255` / `color::div255_round`。
    理由是新增孪生函数等于把慢实现留在库里等人误用，而替换可以证明是逐位等价的，没有理由保守。
  - `div255` 用 §2.2 的 `((x + 1) * 257) >> 16` 形式，且是**精确**的，不是近似：
    `div255_is_exact_over_its_whole_domain` 对 `0..=65535` 全域穷举比对 `/255`。
  - **边界警告（给 Phase 3 实现者）**：`(x + 1 + (x >> 8)) >> 8` 这个同样常见的写法在
    `x <= 65534` 全部正确，**唯独 `x == 65535` 会给出 256 而正确值是 257**。若在汇编里图省事
    改成该形式，症状会是全屏渐变里某一档色阶偏一格，极难定位。已用
    `div255_is_exact_at_the_top_of_its_domain` 钉住。
  - **另一处陷阱**：§2.2 列出的"嵌入式经验公式 `((x + 1) * alpha) >> 8`"与 `x / 255` 不是同一个
    函数，不可替代，勿采用。
  - 另外 §2.2 写的是 `x / 255`，但此处代码实际做的是四舍五入的 `(x + 127) / 255`，两者不等价；
    故拆成 `div255` 与 `div255_round` 两个函数，后者即 `div255(x + 127)`。
- [x] **Phase 2: 搭建 `arch` 抽象层与基准测试**
  - `src/arch/mod.rs` + `src/arch/fallback.rs`，导出 `blend_span_rgb565` / `blit_mask_span`，
    与 §2.3 的接口签名一致（`mod.rs` 内已写好 Phase 3 的 `cfg` 插入位置）。
  - 调用点已全部改走该接口：`raster::fill_rect`、`fill_rrect`、`fill_circle`、
    `fill_convex_quad` 的半透明中段，以及 `raster::blit_mask`（由逐像素改为**逐行切片**）。

## 五、 Phase 2 基准实测与结论

`cargo run -p pomelo-gfx --release --example bench_spans`，480×480 RGB565，宿主 x86-64。
**绝对数字不可用于真机推断**（见下第 3 条），能用的只有横向次序。

| 内核 | ns/px | 折算整屏 ms | 实测像素数 |
| :--- | ---: | ---: | ---: |
| `fill_rect` 不透明 | 0.013 | 0.00 | 230400 |
| `fill_rect` alpha 180 | 0.399 | 0.09 | 230400 |
| `fill_rrect` 不透明（胶囊形） | 0.020 | 0.00 | 230400 |
| `blit_mask` 不透明（文字） | 0.656 | 0.15 | 403200 |
| `blit_mask` alpha 180 | 0.791 | 0.18 | 403200 |
| `blit_mask` 稀疏墨迹（floor 200） | 0.444 | 0.10 | 403200 |
| `blit_mask` 空覆盖率窗口 | 0.246 | 0.06 | 64000 |

三行 `blit_mask` 是同一内核在三种墨迹密度下的读数，它们与上面的填充行**不可比**：空覆盖率那行
几乎没有做混合，它的 ns/px 是"判断不需要混合"的代价。基准的输出里已写明这一点。

### 结论 1：Phase 1 换来的是 11%，不是数量级

`blit_mask` 不透明 vs alpha 180 之差（1.032 vs 1.157，改动前）**11%**，这就是"跳过合并两个
alpha 的乘加与除 255"所值。原因很直接：这条路径的每一像素还要读一个 mask 字节、判断是否为 0、
并调用 `blend_rgb565`，而三个通道的定点算术在这堆开销里占比很小。

Phase 1 仍然值得做——它是精确的、可测的、零风险的，且是 Phase 3 的前提——但**不要指望
靠它拿到 §3 承诺的 2x~3x**。那个倍数必须来自别处，而且确实来自别处了：见结论 1b。

### 结论 1b：真正的收益在分支，且已用可移植 Rust 拿到 37%

改动前的 `blit_mask` 是 `fill_rect` alpha 的 **2.7 倍**（1.032 vs 0.387），而两者每像素的算术
**完全相同**（都是 `blend_rgb565`）。多出来的 1.7 倍只可能是：每像素多一次 mask 字节读取，
加上 `if coverage == 0 { continue }` 这个跳零分支——真实字形蒙版有 60%~70% 的零覆盖率，
等于在一个近乎随机的位上反复分支，预测器基本失效。

据此把内核改成"行内无分支"，并**实测**（这是关键，不是推断）：

| 内核 | 逐像素分支（原） | 仅无分支 | + 逐行空行跳过 |
| :--- | ---: | ---: | ---: |
| `blit_mask` 不透明 | 1.032 | 0.640 | **0.648**（-37%） |
| `blit_mask` alpha 180 | 1.157 | 0.752 | **0.765**（-34%） |
| `blit_mask` 空覆盖率 | 0.262 | 0.563（**劣化 2.1x**） | **0.209**（-20%） |

中间那一列是本阶段最有价值的一条教训：**无分支在混合覆盖率下大赢，在零覆盖率下大输。**
空覆盖率不是角落情形——裁剪一个字形时，被裁掉的大部分正是它自己的透明边距。所以正确的形状
不是"全部无分支"，而是**一行一个可预测的分支 + 行内零分支**：空行整行跳过，有墨的行不做任何
逐像素判断。最终三档密度**全部**优于原实现。

`blend_rgb565_unconditional` 之所以能存在，是因为 `blend_rgb565` 的两个提前返回**从来不是
正确性的一部分**——通用公式在 alpha=0/255 本来就直接返回 dst/src。这一点由
`blend_rgb565_unconditional_agrees_at_the_ends_it_dropped` 全域钉住；否则丢掉那两个 `if`
会在某些覆盖率上合成出错误的字形，而那种 bug 看起来像字体问题。

**这抬高了 Phase 3 的门槛**：§2.2 原本设想的那类收益，其大头已经被可移植的安全 Rust 拿到。
剩下留给 8 lane 并行化的只有算术本身，而真机瓶颈很可能在访存（结论 3）。

同理，`blend_span_rgb565` 与 `blit_mask_span` 的矢量版收益并不对等：前者每像素无 mask 读取、
无数据相关分支（alpha 在整条 span 内是循环不变量），矢量化上限有限；后者才是该投入的地方。

### 结论 2：Phase 3 的 PIE 内核该长什么样

由结论 1b 直接得出：一次载入 8 字节 mask 与 8 个像素，**8 个 lane 全部无条件混合**，用 mask 值
本身（而不是分支）控制贡献量；空行的跳过留在**行**一级，不进 lane。跳零在标量里是"省一次
乘法"，在矢量里却是"引入一个无法预测的分支去省 1/8 的工作"，方向相反。
`arch::fallback::blit_mask_span` 现在的形状（函数开头一次行判空 + 行内零分支）就是该内核的
标量预览版，两者应当逐行同构。

### 结论 3：真机数据是 Phase 3 的唯一判据

README 记录真机纯色矩形填充约 **0.12 µs/像素 = 120 ns/像素**，而此表同一项是 **0.014 ns/像素**，
相差约 **4 个数量级**。这不是编译器差异能解释的：480×480 的整屏填充按 PSRAM 带宽应在毫秒级，
而 120 ns/像素意味着约 28 个周期写一个 4 字节字。合理的解释是**逐 cache line 的写分配
（write-allocate）**——每写一个 32 字节行就要先从 PSRAM 读回整行，于是瓶颈完全落在访存而非算术。

若真如此，则对**大面积填充**做算术矢量化的收益接近于零（§2.1 表中 `fill_u16_slice` 那一行
"吞吐提升 4 倍"尤其存疑：现在的 32 位双像素写已经够快了，真正的限制在 cache line 是整行写
还是部分写）。反倒是让每次写**覆盖完整 cache line** 可能比加宽位宽更有意义。

在这个问题被真机数据回答之前，Phase 3 的投入规模无法判断。**所以下一步不是写汇编，而是先把
这四个 Phase 2 内核编进固件复测**（Phase 4 的前半），拿到 `blit_mask` / 半透明填充的真机 ns/px，
再决定 PIE 汇编该覆盖哪些内核、值不值得。

### 尚未处理、与本次改动相关的一处

`raster::blit_image_565_with_alpha` 仍是逐像素混合，未走 `arch`。它每像素的源色都不同，
套不进 `blend_span_rgb565`（常量色）的签名，需要第三个内核（带 per-pixel 源色）才能批量化。
本次未动；但它已自动受益于 `blend_rgb565` 的定点化。带 alpha 的图标/图片若在帧中占比可观，
应作为独立一项评估。

> 由结论 1b 补记：该函数每像素的 alpha 同样来自数据（图片的 alpha 通道），因此它与
> `blit_mask_span` 面对同一个"数据相关分支"问题。若它值得优化，走的应该是与结论 1b 相同的路，
> 而不是等 PIE。它的签名需要一个 `blend_rgb888_onto_rgb565` 的无分支孪生版本。

## 六、 Phase 3 可行性勘定（尚未落笔汇编，本节即其理由）

Phase 3 原计划"用 `core::arch::asm!` 写 128 位块"。动手前先用本机工具链把可行性问清了，
结论是：**能写，但当前不该写**。本节记录取证方法与障碍，使下一步是设计工作而不是逆向工程。

### 取证方法（可复现）

两个问题各有一个确定性的答案来源，都不靠记忆：

1. **汇编器接受什么**：本机装有 `esp198` 工具链。建一个 `no_std` 探针 crate，把每个候选
   助记符放进各自独立的函数，使错误信息能指名到行，然后
   `cargo +esp198 build --target xtensa-esp32s3-espidf -Zbuild-std=core`。
   （`rust-src` 已安装，`core` 从源码构建，单次约一分钟。）
2. **助记符的真名**：LLVM 的指令名字符串表就在
   `~/.rustup/toolchains/esp198/bin/rustc_driver-*.dll` 里。按 `ee\.[a-z0-9.]+` 提取该区段，
   一次拿到全部 213 条 PIE 助记符。**这一步否掉了我按记忆猜的全部 add/sub/shift 名字**，
   是本次收益最高的半小时。

### 障碍 A：`asm!` 在 xtensa 上需要 nightly feature 门禁

编译报 `E0658: inline assembly is not stable yet on this architecture`。修法是
`lib.rs` 加 `#![cfg_attr(target_arch = "xtensa", feature(asm_experimental_arch))]`。
这不影响宿主构建（门禁只对 xtensa 目标生效），且固件本来就在 nightly 上
（配方是 `cargo +esp198 build -p rust_main --target xtensa-esp32s3-espidf -Zbuild-std=std,panic_abort --release`）。
所以这是**低**成本障碍，但必须先加，否则 Phase 3 连编译都过不去。

### 障碍 B（真问题）：q0~q7 无法作为 asm 操作数具名

`out("q0") _` 报 `invalid register 'q0': unknown register`。地址寄存器则可以具名
（`in("a3")` / `in("a4")` 实测通过）。

后果不是"写不了"，而是**无法声明矢量寄存器被破坏**。矢量寄存器只能以字面量出现在指令文本里，
编译器不知道它们被改过。两条出路：

- **(a) 继续用函数内 `asm!`**：依赖"LLVM 在纯标量代码里永不分配 q 寄存器，故未声明的破坏是
  无害的"。在本仓库当前代码下这个假设成立（没有任何 128 位向量类型），但它是**没有任何编译器
  检查兜底的承重假设**——将来某次改动若让 LLVM 用上 q 寄存器，症状是随机的数据损坏。
- **(b) 用 `global_asm!` 或 naked 函数整函数手写**：不经过寄存器分配器，因此无需声明破坏。
  代价是要自己处理 windowed ABI 的 `ENTRY`/`RETW` 序言尾声（`target_feature="windowed"`），
  且 `naked_asm!` 亦为 unstable。

(a) 更简单，(b) 更正确。**这个选择应该在有真机数字之后再定**，因为 (b) 的成本只有在收益确定时
才付得起。

### 已确认可用的助记符（本机汇编器）

实测编译通过（非从表推断）：`ee.vld.128.ip`、`ee.vst.128.ip`、`ee.zero.q`、`ee.vldbc.16`、
`ee.andq`、`ee.orq`、`ee.zero.qacc`、`ee.vmulas.s16.qacc`、`ee.movi.32.q`，以及
`in("a3")`/`in("a4")` 具名地址寄存器。

从字符串表提取的真名清单里，与本次内核直接相关的还有：
`ee.vadds.s16`、`ee.vsubs.s16`、`ee.vmin.s16`、`ee.vmax.s16`、`ee.vmul.{s16,u16}`、
`ee.vmulas.{s16,u16,s8,u8}.qacc`、`ee.vsmulas.s16.qacc`、`ee.vcmp.{eq,gt,lt}.{s8,s16,s32}`、
`ee.vzip.{8,16,32}`、`ee.vunzip.{8,16,32}`、`ee.mov.{s16,u16}.qacc`、`ee.movi.32.a`、
`ee.slci.2q`、`ee.srci.2q`、`ee.src.q`、`ee.ldqa.{u8,u16}.128.ip`、`ee.srs.accx`。

**三条会直接改写内核设计的差异**（对照 §2.1 按记忆列的那张表）：

1. 加法/减法是 **`vadds.s16` / `vsubs.s16`**，不是 `vadd.s16` / `vsub.s16`。中间的 `s` 是
   *saturating*——即这两个是**饱和**加减，混合的中间结果若依赖不饱和回绕必须另行处理。
2. 移位**只有 32 位粒度的 `vsl.32` / `vsr.32`**，没有 16 位粒度的 `vsl.16` / `vsr.16`。
   这是硬约束：RGB565 的 5-6-5 三通道拆解需要在 16 位 lane 内做移位，而 PIE 不提供。
   可用的替代是 `ee.srci.2q`（立即数移位）、`ee.src.q`、以及 `ee.vzip.16`/`ee.vunzip.16`
   做 lane 重排——**内核的数据布局要按这些指令能做的事来设计，而不是按直觉的 5-6-5 拆解**。
3. `ee.vldbc.16`（广播一个 16 位标量到 8 个 lane）与 `ee.ldqa.u8.128.ip`
   （载入 16 字节并**解包**进 QACC）恰好是文字内核要的那两个原语：前者把颜色广播开，
   后者把 mask 一次读进来。这是 §2.3 接口签名能对上 PIE 的正面证据。

### 为什么现在不写

三条合起来：

1. **无法执行验证。** 本机可以证明汇编*能过汇编器*，不能证明它*算得对*。lane 顺序、字节序、
   饱和行为、QACC 的符号语义，每一项都需要真机运行才能确认。一个"能编译但算错"的内核刷进固件
   只会得到错像素，而且无法区分是算法错还是汇编错。
2. **收益空间已被结论 1b 大幅吃掉**，且真机瓶颈很可能在访存（结论 3）。
3. **障碍 B 的取舍取决于收益大小**，而那要等真机数字。

因此本阶段交付的是：可移植的 37% 收益（结论 1b）+ 本节的可复现勘定结论。
**建议顺序不变：先跑 Phase 4 的真机基准，拿 `blit_mask` 与半透明填充的真机 ns/px，再决定
是否为 PIE 付 (b) 方案的成本。** 如果那时仍要写，本节的三条差异是设计输入而非待解之谜。

## 七、 Phase 4 真机实测（已取得）

基准已接进固件并跑通真机。接入方式：`pomelo-gfx` 新增 `bench` 特性，把宿主示例里的测量逻辑
上移为 `crate::bench`，于是**宿主与设备跑的是同一份代码**——否则两边数字不可比。固件侧由
`render-debug` 特性在 `board.init()` 之后、UI 启动之前调用一次。

复现：

```text
idf.py -DPOMELO_RUST_FEATURES=render-debug -p COM3 build flash
# 或宿主：cargo run -p pomelo-gfx --release --features bench --example bench_spans
```

**测试机**：ESP32-S3 @240MHz，8MB octal PSRAM（32 字节突发，固定 10 周期读延迟），480×480
RGB565，ESP-IDF v6.1，`opt-level="s"` + LTO + `codegen-units=1`。控制台走 USB-Serial/JTAG。

### 7.1 孤立内核：整机是访存瓶颈，算术占比极小

| 内核 | 真机 ns/px | 宿主 ns/px | 倍数 |
| :--- | ---: | ---: | ---: |
| `fill_rect` 不透明 | 57.61 | 0.013 | 4432x |
| `fill_rect` alpha 180 | 216.04 | 0.400 | 540x |
| `fill_rrect` 不透明 | 17.94 | 0.020 | 897x |
| `blit_mask` 不透明（文字） | 321.15 | 0.641 | 501x |
| `blit_mask` alpha 180 | 312.50 | 0.764 | 409x |
| `blit_mask` 稀疏墨迹 | 178.75 | 0.446 | 401x |
| `blit_mask` 空覆盖率窗口 | 46.97 | 0.214 | 219x |

两次独立烧录的读数差异 **< 0.3%**，测量本身可信。

**倍数栏才是本节的重点。** 宿主大约是这台芯片的 15 倍主频。若一个内核的代价纯粹是算术，它的
真机/宿主倍数应当在 15 上下。实际倍数是 400~4400。也就是说：

- `fill_rect` 不透明的真机耗时是"纯算术假设"的 **295 倍**；
- `blit_mask` 不透明是"纯算术假设"的 **33 倍**。

差额只能是访存。**这两个内核的真机代价有 97%~99.7% 不在算术上。**

最直接的一条证据是这两行：

```text
blit_mask opaque (text)   321.153 ns/px
blit_mask alpha 180       312.500 ns/px
```

二者唯一的差别，是后者每像素多算一次 `div255(alpha * coverage)`。**在真机上这个差值落在噪声里
（-2.7%，而两次烧录之间的噪声是 ±0.3%）。在宿主上同一对数字相差 19%。** PIE 要并行化的正是
这类逐像素算术，而它在真机的 `blit_mask` 里已经测不出来。

### 7.2 真实帧：最大的相位是 `quads`，不是文字

`[phase]` 行仍由 `render-debug` 输出。抓取 419 帧（其中 108 帧真的做了绘制）：

| 相位 | 峰值 ms | 均值 ms | 对应内核 |
| :--- | ---: | ---: | :--- |
| `clear` | 14.75 | 1.48 | `fill_rect` |
| `quads` | **41.94** | **2.28** | `fill_rect` / `fill_rrect`（含半透明） |
| `text` | 35.30 | 2.25 | `blit_mask` |
| `raster` | 18.07 | 0.16 | 字形栅格化——非 span 内核，矢量无用 |
| `blit` | 15.39 | 1.31 | `blit_mask` |
| `total` | 277.45 | 13.66 | |

**这推翻了 §1 的前提。** 计划书假设"文字占整帧约 60%"，据此把矢量化优先级给了文字路径。
真机数据里填充与文字**基本相当**：

- 峰值：`clear + quads` = 56.69ms vs `text + blit` = 50.69ms
- 均值：`clear + quads` = 3.76ms vs `text + blit` = 3.56ms

若只优化文字路径，上限是砍掉约一半的绘制时间；而 `quads` 是**单相位最大者**。

另有 73/419 帧超出 16.7ms（60fps 预算），最差一帧 277ms。

### 7.3 基准的预测能力已被真机验证

基准预测整屏 `fill_rect` = **13.27ms**；真机 `clear` 相位峰值 **14.75ms**（均值 1.48ms，因为多数帧
只清一小块脏矩形）。**相差 10% 以内。**

这条验证的意义：孤立基准对访存型填充的预测是可信的，§7.1 那张表可以当作决策依据，而不是
一组"host 上好看的数"。

### 7.4 一处需要修正的读法：文字那一行是上界，不是典型值

真机有一帧画了 264 个字形，`text` 相位 20.23ms —— 合每字形 **76.6µs**。而基准合成字形（28x24，
覆盖率铺满整个包围盒）预测 **215.7µs**，是前者的 2.8 倍。

原因正是结论 1b 那条：合成掩码在整个包围盒里都有墨，**逐行空行跳过永远不触发**；真实字形在
升部以上、基线以下和两侧边距都是空行，跳过大量生效。所以：

- `blit_mask opaque (text)` 是**最坏情况上界**；
- 真实文字落在 `hairline`（178.75）与 `opaque`（321.15）之间，更靠近前者。

读这张表时不要用 `opaque` 行去乘真实字形数。

### 7.5 Phase 3 的修订结论：**不建议现在写 PIE**

由 7.1 直接得出。PIE 能改的是两件事：逐像素算术的条数，以及 load/store 的**指令条数**。它改不了
搬运的**字节数**，也改不了 PSRAM 的带宽与延迟上限。

- 算术那一项：在真机上测不出来（7.1 末尾那两行）。
- 指令条数那一项：8 lane 一次 `vld.128` 确实能减少访存指令，这是 PIE 唯一还剩的正当理由。

但为了这一项去付 §6 障碍 B 的 (b) 方案成本——手写 windowed ABI 的 `ENTRY`/`RETW`，且完全无法在
本机验证——**在拿到这个量级的证据后不成立**。收益的绝对值太小，风险与调试成本太高。

### 7.6 数据指向的下一个着力点（不是 PIE）

`fill_rect` 不透明达到 **34.7 MB/s**（230400px x 57.61ns = 13.27ms 搬 460800 字节），合
**13.8 周期/像素**。一个纯写入的循环在 240MHz 上是这个速度，说明**约束在存储路径上**，而不是
在里面那几个移位与或运算上。

这条签名与"写分配（write-allocate）"一致：每次跨入新 cache line 时，行要先被取回再写入，等于
写带宽减半。**这是假设，不是本次测得的结论**——要坐实需要看面板缓冲的映射方式（cacheable /
non-cacheable / write-through）并做对照实验。

之所以值得优先验证：它同时指向**最大的相位**（`quads`）和**真机最差的内核**
（`fill_rect alpha 180`，216.04 ns/px，是写-only 填充的 3.75 倍——这 158 ns/px 的差额里，读目标
像素只是其中一部分，剩下的是算术，但算术已证明在 `blit_mask` 上测不出来，此处却很大，值得专门
拆开）。**先花一天验证存储路径，比先花一周写无法验证的汇编更可能改善帧时间。**

### 7.7 本次固件侧的一处缺陷（已修）

接入的第一版用了"固定迭代次数 + 全局除数"，真机上那是 47 秒的紧循环，把 CPU0 的 idle 任务饿死
5 秒，**触发了任务看门狗**：

```text
E (7473) task_wdt: Task watchdog got triggered.  - IDLE0 (CPU 0)
```

根因是单个内核的每次调用代价差了三个数量级（`fill_rect` 13ms vs `blit_mask` 130ms），一个全局
除数不可能同时适配两端。改为**按时长预算自适应**（先测一次调用，再按 50ms 预算反推迭代次数），
于是：真机总耗时 **47s → 2.9s**，看门狗 **0 次**，且宿主数字与改动前完全一致。

教训值得记：**这个缺陷不会出现在数字里，只会出现在控制台上。** 一个只看 ns/px 表格的验收流程
会把它整个漏掉。
