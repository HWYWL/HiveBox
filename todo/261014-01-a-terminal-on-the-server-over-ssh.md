# 待办规划: 在服务器监控里加一个终端 —— 点一下就在那台机器上敲命令

- **所属模块**: `pomelo-hal/src/traits/nas.rs`、`pomelo-firmware/firmware/pomelo-hal-esp32/src/nas.rs`、`pomelo-apps/nas-monitor`、`pomelo-apps/terminal`、`pomelo-apps/app-launcher`
- **目标平台**: ESP32-S3（480×480 AMOLED；无物理键盘，输入走 `pomelo_widgets::touch_keyboard`）+ Desktop Simulator
- **创建日期**: 2026-10-14
- **状态**: 已实现并发布（2026-10-14，`v0.8.0-20261014`）—— 入口按决策 1 的**甲**、开在终端应用按决策 2 的**甲**，但会话形态**没走建议的甲（逐条 exec），走的是乙（真 PTY shell）**：`pty()` + `shell()` + `xterm-256color`，代价是一层 ANSI 解释器（`terminal/src/screen.rs`），换来 `cd`/`export`/颜色/进度条都成立；决策 4（各自一条连接）、决策 5（`Leave` 回本地）照建议做
- **关联**: `261004-01`（开源库集成与架构）、`NasBackend` 契约、`sunset`（纯 Rust 的 SSH 客户端）

## 一、 结论摘要

1. **两半边都在仓库里，缺的是把它们接起来的那一段通路。** 终端应用在 `pomelo-apps/terminal`，SSH 客户端在 `pomelo-firmware/firmware/pomelo-hal-esp32/src/nas.rs`（`sunset`，板端 1369 行）。今天这两者之间没有任何一条线：`terminal/Cargo.toml` **不依赖 `pomelo-hal`**，它的命令全部落在板子自己的存储上。

2. **终端的执行口只有一处，位置正好。** `shell.rs:337` 的 `execute_command` 里只有一行：`crate::commands::get_registry().dispatch(self, cmd)`。要加「远端模式」，分支就加在这一个函数里。

3. **真正的工作量在 SSH 那一侧，不在界面。** 现有后端为「监控」做过两个明确取舍：**一次 look 新开一个会话**（`nas.rs:24-28`）、**一次只做一件事**（`nas.rs:16-22`）。终端要的是「一个会话里连着敲」，这两条都得重新谈一次 —— 尤其会话保持与否，决定了敲一条命令是**等 1 秒**还是**等 0.02 秒**。

4. **`sunset` 支持真 PTY shell。** `channel.rs:1178` 有 `pty()`、`:1187` 有 `shell()`、`:1191` 有 `exec()`。所以「真终端」（`cd`、`top`、`vi` 都能用）**不是做不到**，而是要多做一层：流式输入、流式输出、ANSI 转义。

5. **软键盘不是障碍。** `touch_keyboard` 四个页面里，命令离不开的 `-` `/` `:` 在数字页、`_` `\` `|` `~` `$` 在符号页（`keys.rs:437-456`），一个不缺。只是敲 `docker ps -a` 要点二十几下。

6. **跨应用传参数在仓库里没有先例。** 启动器只有 `get_or_create_*(&mut self)` 这类「拿到或新建」的入口（`app-launcher/src/lib.rs:581`、`:617`），没有「打开某个应用并带上一个参数」这条通路。**这次要新开这个口子**，而且最好只开一次、开得能被别的应用复用（比如将来「文件」直接打开某个目录）。

### 两条既有取舍，以及为什么终端和它们冲突

**「一次 look 一个新会话」**（`nas.rs:24-28`）的理由是硬的：保持的会话要扛住 NAS 重启、路由器掐闲置连接、服务器自己的 idle timeout，而这三种失败**都是静默的** —— 会出现在「有人正好在看那块面板」的那一次 look 上。握手对一台醒着的机器是 look 里便宜的那一半，所以它每次都重付一遍，从一个确定好的连接开始。

终端要的恰好相反：`cd /volume1` 敲一次，下一条命令得还在那个目录里；每条命令重付一次握手，那就不叫终端了。**所以终端这条路必须保持会话**，并且自己承担上面那三种失败 —— 这是这次要新增的一份状态，不是复用 look 的那一份。

**「一次只做一件事」**（`nas.rs:16-22`）的理由同样硬：worker 一次只跑一个 look，请求不会排成队互相超车。终端是**用户驱动的**，它的节奏由手指决定，和每秒一次的 look 节拍无关。两者共用一个 worker 就意味着一次 `docker ps` 会把监控的刷新顶掉一拍；各自一条线程则要多一份 PSRAM 栈（现有那份是 32 KB 级别的量级，`nas.rs:106-117` 讲了为什么必须放 PSRAM）。

## 三、 真正缺的东西

### 1. HAL 上要多一个「跑一条命令」的口（`pomelo-hal/src/traits/nas.rs`）

形状照抄现有的 start-and-poll，因为理由一模一样（一次命令是几百毫秒，UI 帧花不起）：

```rust
/// 在一台机器上跑一条命令。立刻返回。
fn shell_send(&mut self, host: &str, line: &str) -> Result<(), HalError>;

/// 自上次以来远端说了什么。便宜、可每帧读。
fn shell_output(&self) -> Option<RemoteOutput>;
```

`RemoteOutput` 至少要有：`host`、`lines: Vec<...>`、`status`（连接中 / 就绪 / 掉线 + 原因）、以及**会话是否是新的**（终端的提示符要能说出「重连了」）。

### 2. 板端要有第二条会话（`pomelo-hal-esp32/src/nas.rs`）

- 决定会话怎么保活、什么时候判定掉线并重连一次；
- 决定它和 look 的 worker 是**同一线程两个会话**还是**两条线程各一个会话**（见 §四.3）；
- 遵守「PSRAM 栈不许碰 flash」这条：终端的路径上不能有 `known_hosts` 的读写 —— 现有的做法是 `EspNas::new` 读一次、`refresh` 写回（`nas.rs:60-63`），新的与会话也要走同一套。
- 桌面模拟器（`pomelo-hal/src/sim/nas.rs`）要给出一个假实现，否则桌面测试全挂。

### 3. 终端要有「远端模式」（`terminal`）

- `TerminalModel` 增加会话概念：`Local` / `Remote { host, user }`；
- `execute_command`（`shell.rs:337`）在远端模式下把整行发出去，而不是 `dispatch`；
- 提示符：远端时 `user@host$`（本地的 `cwd` 概念在远端不成立；若走 PTY，远端 shell 自己会画提示符，那就该**不再自己画**）；
- 输出回来要有换行、要有滚动到底 —— `auto_scroll_to_bottom` 这套已经有了。

### 4. 监控页要有一个入口，并且要能把「哪台机器」带过去

- `nas-monitor` 需要一个新 `Message`（比如 `OpenTerminal`），只有 `self.watched` 存在时才发得出来；
- 启动器要接住它：`get_or_create_terminal()` → 把它切到远端（带上 host）→ `screen = Screen::App(TERMINAL)`。这是 §二 里说的**新口子**。

### 5. 一个「谁的会话」的所有权规则

写清楚：终端开会话时，监控的 look 是照旧跑、还是让路；终端退出/掉线时谁负责把会话收掉。不写清楚就会变成那种「过一会儿才有人发现 NAS 连不上了」的问题。

## 四、 要拍板的决策

1. **入口放在哪。**
   （甲）页头第二行、`硬盘` 标签**右边**、编辑铅笔左边，加一个「终端」按钮 —— 和编辑铅笔同排，那一排本来就是「对这台机器能做的事」；
   （乙）`硬盘` 那一页（`Tab::Disks`）的表头上方单独一行；
   （丙）概览页里「硬盘读写」那张卡片旁边。
   建议**甲**：它是唯一一个「换到哪一页都在」的位置，而终端是整台机器的能力，不是硬盘那一页的能力。

2. **点下去开在哪儿。**
   （甲）**复用终端应用**：跳到它、切到远端模式，提示符变成 `user@host$`。好处是键盘、历史、回滚、配色、`help` 全都是现成的，且**只有一套终端**；
   （乙）**在监控应用里内嵌一页终端**：不用碰启动器、不用跨应用传参，但仓库里从此有**两套终端界面**（`261006-01` 的文档里已经把这笔账算过一次：「每加一个要输入的地方就要再手搓一遍」）。
   建议**甲**。

3. **会话形态：一条一条 exec，还是一个真 shell。**
   （甲）**逐条 exec**：一行 = 一个 `exec` 通道，会话保持（连接与认证只做一次）。稳、输出干净、没有 ANSI 要处理。代价是 `cd`、`export`、`top`、`vi`、管道里的交互式工具都不成立 —— 能干的正是「看一眼、查一条、跑一条」。
   （乙）**PTY shell**：`pty()` + `shell()`，真终端。代价是多一整层：流式输入、流式输出（`\r` 进度条、ANSI 颜色、清屏、光标定位），以及 480×480 上跑 `vim` 是什么体验这件事本身。
   建议**先做甲**，并把「要不要乙」留成下一步 —— 甲把 HAL 的那条通路（会话保持、掉线重连、输出回传）都建好了，乙是把它换成一个流式的实现，不会白做。

4. **终端会话与监控 look 的关系**（见 §二）：建议**各自一条会话**，因为让路意味着「打开终端，监控数字就停了」，而用户点终端时多半还想瞟着监控。

5. **远端模式是不是要能回到本地**：建议给一个明确的退出口（比如远端时提示符旁边一个「本地」按钮），否则进了远端就出不来了。

## 五、 实施步骤（建议顺序）

1. **先把 HAL 的口开出来**：`NasBackend` 加两个方法（默认实现给「不支持」，桌面模拟器给假数据），`cargo test --workspace` 全绿。这一步不碰板子，也还没有界面。
2. **板端做会话保持**：在 `pomelo-hal-esp32/src/nas.rs` 里做出「一个保持的会话 + 逐条 exec」，含掉线判定与重连一次。**先只跑一个固定的命令**（比如 `uname -a`）验证通路，别急着接界面 —— 这一步的坑全在 SSH 侧。
3. **终端加远端模式**：模型、提示符、`execute_command` 的分支，桌面模拟器上就能把交互跑通（模拟器给了假输出）。
4. **监控页加入口 + 启动器接住消息**：这是唯一一处跨应用的新通路，单独做、单独测。
5. **接上真机验证**：真 NAS 上敲 `ls`、`df -h`、`docker ps`，看会话是否保持、掉线后是否重连、监控数字是否照常刷新。
6. **再决定要不要 PTY shell**（决策 3 的乙）。

## 六、 代价与风险

- **镜像体积**：`sunset` 本来就在镜像里（监控在用），增量是会话保持那一份状态与代码。要记进 `firmware.bin` 的账，别当成回归。
- **内存**：多一条保持的会话（TCP + 会话状态），若选「另一条线程」还要再一份 PSRAM 栈。这条必须**在真机上量**，不能推算。
- **`exec` 通道没有 stdin**：逐条 exec 模式下，任何「等你输入」的命令（`sudo` 问密码、`apt` 问确认）会**挂住**直到 `LOOK_DEADLINE` 那一类的超时。要有超时和「这条命令没有结束」的提示，否则用户会以为板子死了。
- **输出的量**：`cat` 一个大文件、`journalctl` 一把日志，会把几百 KB 塞进内存再塞进文字记录（现有记录只留 64 行，`shell.rs:340-344`）。要定一个「一条命令最多收多少字节」。
- **PSRAM 栈不许碰 flash**（`nas.rs:55-63`）：新的会话路径要遵守同一条，否则是随机崩溃而不是报错。
- **跨应用传参是新口子**：一次要做对（谁清参数、应用不在运行时要怎样），否则会变成那种「第二次进去还是上次那台机器」的怪问题。
- **真机验收成本**：这一条必须连着一台真的、开着 SSH 的 NAS 才能验，模拟器只能验交互。

## 七、 不做这件事的代价（也就是维持现状）

- 服务器上出问题的时候，面板只能**看**，要动手还是得去开电脑、开一个终端、`ssh` 进去 —— 而这块板子就摆在旁边，正是为了「不用开电脑」。
- `pomelo-apps/terminal` 会一直是一个**只看得见板子自己**的终端：它能 `ls` 板子的 `/internal`，却对网络那一侧完全无用。
- 监控页会一直是**只读**的：`NasBackend` 只有「看」的口，没有「做」的口，将来任何「在服务器上做一件事」的需求（重启一个容器、清一次缓存、看一下 `docker logs`）都要从零开始。
